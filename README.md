Docker helper scripts (dev & prod):

- **`npm run docker:dev:build`**: build images from `docker-compose.dev.yml`.
- **`npm run docker:dev:up`**: run `docker-compose -f docker-compose.dev.yml up` (starts dev containers, e.g., Redis, app, etc.).
- **`npm run docker:dev:down`**: stop dev containers.
- **`npm run docker:dev:clean`**: stop dev containers and remove volumes (`down -v`) — useful to reset data volumes.
- **`npm run docker:prod:build`**: build images from `docker-compose.prod.yml`.
- **`npm run docker:prod:up`**: run production compose stack.
- **`npm run docker:prod:clean`**: stop production compose and remove volumes.
- **`npm run docker:clean:all`**: run clean for both dev and prod compose files.

Use these scripts to orchestrate dependent services locally (Redis, etc.). For example, to start the complete local environment:

```bash
npm run docker:dev:build
npm run docker:dev:up
```

To tear down and remove volumes (data):

```bash
npm run docker:dev:down
npm run docker:dev:clean
```

Notes: when running builds or production stacks you may need to provide valid environment variables for Firebase, Redis, and the API-Football key.

## Redisearch caveat and manual recovery

Known limitation: the current RediSearch integration does not recover automatically when the Redis indexes are missing while there is already data present in the database. In other words, if you (for any reason) have data persisted (for example in Firestore or Redis JSON keys) but the RediSearch indexes were removed or never created, the search layer will not return correct results and the codebase does not yet implement an automatic reindexing flow for that case.

Workaround (manual recovery):

1. Manually delete the persisted data that must be reindexed. This usually means clearing the Redis JSON keys and any persistent volumes containing index metadata. If you are using the local Docker compose stacks, the quickest way to remove persisted volumes and force a fresh start is to run the dev clean script:

```bash
npm run docker:dev:clean
```

2. Start the dev stack again to recreate containers and indexes:

```bash
npm run docker:dev:up
```

3. Re-populate data either by running the background jobs or by exercising the UI which will enqueue store jobs and repopulate indexes.

Important: this process is time-consuming because it requires removing stored data and letting background jobs re-fetch and reindex everything. There is not yet an automated solution for rebuilding indexes from existing persisted data; if you need this functionality we should implement a reindex job that reads persisted documents and re-creates RediSearch indexes and JSON documents in Redis.

Build / production note: the same caveat applies when running production builds or production compose stacks — if indexes are missing but data exists, manual removal and a restart (or an explicit reindex job) are required. For local dev the `docker:dev:clean` + `docker:dev:up` sequence is the recommended recovery; for production you should plan an explicit reindex strategy or schedule a maintenance window to rebuild indexes.

## How the data flow works (end-to-end)

1. UI pages call internal API routes (e.g., the routes under `app/api/*`) or import server-side services from `features/*/services`.
2. Service layer checks Redis (via `lib/redis.ts`) for cached results and uses RediSearch indexes for fast queries.
3. If data is missing or stale, a job is enqueued using `lib/queue.ts` and registration is done through `lib/job-registry.ts`.
4. Worker processes (in `lib/worker.ts` / `lib/worker-entry.ts`) pick up jobs, call `lib/api-football.ts` to fetch remote data, then persist to Firestore (`lib/firebase.ts`) and cache documents in Redis using JSON and RediSearch index updates (`lib/redis.ts`).
